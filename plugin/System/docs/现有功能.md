# 系统基础应用现有功能

本文梳理公开基础插件 `System`。它是 SmartAdmin 的通用后台控制面，业务订单、客户、项目、资产等能力应由独立插件拥有。

## 模块边界

- 提供登录会话、组织权限、租户、文件、日志、通知、调度、字典和平台参数。
- 为业务插件提供治理入口，但不拥有业务插件的数据和状态机。
- 菜单展示、接口权限、数据范围和租户隔离分别承担不同门禁职责。

## 关键流程

### 登录与授权

登录先校验账号和租户状态，再建立 Token 与租户上下文；请求随后经过权限节点和数据范围。菜单可控制入口可见性，但最终接口授权仍以 `#[Auth]` 为准。

### 租户开通

租户、默认部门、租户管理员角色和管理员账号在同一受控事务中创建。平台超级管理员与租户子超管不是同一角色，平台保留权限不会自动下放。

### 文件上传

上传先执行 `prepare`，命中秒传则直接返回；否则选择单次中转、分块中转、单次直传或 OSS multipart，最终通过 `complete` 确认，失败会终止会话。

### 公告与收件

管理员发布公告时生成接收关系；用户的未读、已读和归档只改变自己的收件记录，不回写公告主记录。

### 定时任务

后台只能选择代码注册的白名单任务和表单化周期，不能输入任意命令或 SQL。执行时恢复租户与业务归属上下文，通过数据库锁避免多实例重复，并记录成功或失败结果。

## 安全边界

- 租户隔离先确定业务空间，数据范围再限制该空间内可操作的数据；两者不能互相替代。
- 多角色数据范围采用项目定义的最严格策略，缺少用户上下文时查询应 fail closed。
- 密码、Token、密钥和 Authorization 不明文返回或写入日志。
- 公告接收人、文件下载、用户关系分配和调度 owner 都在服务端复核权限与范围。
- System 配置不用于保存数据库密码、JWT 密钥等高敏运行秘密。

## 合理推测

- System 将继续作为平台控制面，新增具体业务应保持独立插件边界。
- 调度执行器存在替换边界，但当前实现是受控进程内执行，不能宣传为消息队列平台。
- 通知中心当前是站内公告，不应推定已支持短信、邮件或 Webhook。

## 当前不应宣传为已实现

- 通用 CRM、订单、项目、工单或财务业务。
- 以菜单可见代替接口权限，或以前端筛选代替数据范围。
- 任意命令、任意 SQL 或跨租户的定时任务执行。
- 所有存储驱动都支持 OSS 相同的 multipart 直传能力。

## 主要证据

- `plugin.json`：14 个管理页面、74 个按钮权限和模块摘要。
- `readme.md`、`src/Controller`、`src/Service`：当前管理能力和流程。
- `src/Support/TenantSuperPermission.php`、`UploadDriver.php`、调度支持类：关键边界。
- `stc/view`：System 自有管理页面。
- `tests/Unit/System`、`plugin/System/tests/Unit`：权限、调度和页面合同测试。
